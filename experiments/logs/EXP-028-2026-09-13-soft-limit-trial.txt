EXP-028 soft-limit hardware regression — 2026-09-13

Image: servo-zero-test soft-limit revision, built with ESP-IDF v5.5.5.
Hardware: ESP32-S3 QFN56 rev v0.2, CH343 COM4, PCA9685 at 0x40.
Command: host PowerShell Python runner servo_zero_quad_trial.py --port COM4 --cycles 3 --timeout 7

Preflight:
- Three flasher_args.json images were written to COM4; all reported Hash of data verified.
- Boot probe confirmed niulai_servo_zero_test, PCA9685 0x40 ACK, 50 Hz / 400000 Hz I2C,
  CH0-CH7 READY, CH8-CH15 FULL_OFF, and /OE HIGH.
- Runner sent rest and received rest pose reached; holding target; /OE LOW.

Observed sequence:
- key 1 / RF: accepted, complete.
- key 2 / LF: accepted, complete; one I2C NACK recovered by the bounded retry.
- key 3 / RR: accepted, complete.
- key 4 / LR: accepted, complete.
- key 1 / RF: accepted, then four consecutive I2C NACKs at about 805 ms; firmware stopped
  the demo and raised /OE HIGH. Runner sent stop and exited non-zero.

Conclusion:
- The prior cumulative IK/preflight lockout did not recur through four complete steps; the
  software foot workspace limit kept the commanded path bounded.
- The 12-step run was not completed because of a terminal PCA9685 I2C failure, not because of
  the foot-space preflight. No further motion was sent after the failure.
- After this run the Operator reported that CH0/CH1 exceeded the intended hardware boundary.
  This run used the earlier soft-limit image, whose quad q->us guard was still the generic
  `500..2500 us` range; it did not contain the independent directional hip-stop table.
- The board was stopped with `UART stop -> /OE HIGH`. The independent per-channel table and
  runtime gate were added afterward and have only been verified by host/build tests so far.
- Physical direction, actual step/lift, support-leg behavior, current/voltage, noise, and
  temperature were not instrumented by this run and require Operator observation.

  build passed. Image `0xd59a0` was flashed to COM4 and all three image regions returned

- The earlier two 15 mm 4/4 cycles were post-fix unloaded and loaded baselines. The later two 20 mm
  cycles previously described as unloaded were in fact loaded: both reached key 3/RR and then

- Corrected no-load verification with the 20 mm profile completed keys 1 through 4. Final stats:

  The runner sent `stop` and confirmed `/OE HIGH`; key 1 reported `soft_limit_legs=0x01`, keys 2--4

Fast direct-target first physical trial (2026-09-13):
- The fast image `0xd5990` was flashed to COM4; bootloader, app, and partition table all verified with
  `digest matched`.
- In the unloaded `1→2→3→4` trial, key 1 was accepted, then the first active-hold frame produced
  two recoverable PCA9685 NACKs. During key 2's retry path, the ESP32 reported `***ERROR*** A stack
  overflow in task main has been detected` and rebooted. The runner timed out waiting for key 2 and
  sent `stop`; the board ended `/OE HIGH`. Key 2 onward did not complete.
- This is a failed fast-profile safety/robustness trial, not evidence that the no-load hypothesis or
  the fall/NACK causal explanation is correct. The main-task stack is being increased to 8192 bytes
  before any repeat.

Fast direct-target retry after main-task stack fix (2026-09-13):
- Rebuilt with `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192`, producing image `0xd59a0`; the image was
  flashed to COM4 and the three regions returned `digest matched`.
- The unloaded trial accepted key 1, with one I2C software timeout, then accepted key 2. Key 2
  encountered repeated software-timeout/hardware-NACK failures and the firmware stopped at `251 ms`
  with `/OE HIGH`; no stack overflow occurred in this retry. Keys 3 and 4 were not sent.
- Fast direct-target motion therefore remains failed even without load. The result points to an
  unresolved I2C/transport or electrical transient under the larger command jump; it does not prove
  that falling caused the earlier NACKs.
