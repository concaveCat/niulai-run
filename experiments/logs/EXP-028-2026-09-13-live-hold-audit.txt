Deep root-cause review and additional corrections
--------------------------------------------------
The Operator's added test hint was incorporated as three offline scenarios:
one leg held forward, two legs held forward, and rapid repeated forward moves
through all four legs. The implementation review identified these software
causes behind the reported symptoms:

- support retreat previously consumed nominal keyboard distance even when the
  active hip was scaled to 25 percent or saturated at a leg-specific pulse
  limit;
- each support leg was independently clamped, so asymmetric limits could make
  only one or two support feet continue moving;
- live press preflight reused the fixed-duration diagnostic path, allowing a
  failure in a different path to reject a valid live action;
- fixed-hip knee solving checked an endpoint but did not enforce a continuous
  knee branch and monotonic forward foot path;
- press/release inspected shared masks before taking the same mutex used by the
  motion task, so rapid UART key events could observe a stale state.

Corrections made in the working tree:

- support allocation now uses actual FK forward displacement to produce one
  nominal retreat request, then independently caps each support leg by its
  own workspace/pulse capacity; a saturated support leg is held alone while
  the other supports continue;
- live-plan construction is separate from fixed diagnostic-path preflight;
- live swing uses a 32-sample branch/forward-continuity check and first unsafe
  boundary saturation;
- press/release state inspection and mutation are mutex-protected.

Additional focused C coverage includes:

- monotonic offset=0..160 mm live holds for RF/LF/RR/LR;
- simultaneous LF+RR active legs and equal retreat of both supports;
- asymmetric support-limit capacity where only the constrained support bit is
  reported and at least one unconstrained support continues to the nominal
  retreat request;
- 16 rapid RF/LF/RR/LR lift/swing/search cycles using the prior successful
  pose as the next start state;
- live-plan construction without fixed diagnostic-path preflight.

This remains software-only evidence. No flash, UART movement command, or
physical actuator test was performed for this correction pass. The board, if
connected, still contains the previously flashed image, not this working-tree
revision.

Post-flash mechanical observation and semantic regression review
----------------------------------------------------------------
After the later authorized flash and PowerShell sequence tests recorded in
`experiments/logs/EXP-028-2026-09-13-knee-dominant-live-hold-flash.txt`, the
Operator reported that the larger-amplitude walk still retracts the support
legs too little and can leave all four legs leaning forward. The UART
sequence completion and zero/recoverable NACK observations are transport
evidence only; they do not contradict this mechanical observation.

The prior foot-space implementation in this file's `HEAD` version used
explicit X/Z targets followed by full IK:

- support legs used `start_x - stance_step_length_mm * progress`;
- lift used `start_x - lift_back_mm * progress` and rising Z;
- swing used an explicit X path from the lift-back point to the step target;
- SEARCH held the commanded touchdown X while lowering Z.

The current live implementation no longer has those semantics:

- `stance_step_length_mm` is still parsed and logged, but live support
  allocation derives the nominal request from active-leg FK travel and then
  divides by support count;
- the 40 mm/50% software model (45 mm thigh, 70 mm shank, start `(0,-100)`)
  predicts a fixed-hip lift foot X of about `38.13 mm` at Z `-60 mm`, already
  beyond the `+35 mm` actual-foot workspace bound;
- for the same model, the nominal `(30,-60)` endpoint changes hip by about
  `-10.16 deg`, while the local probe selects the opposite positive direction;
  the current `fabs()` therefore discards the required sign;
- at a 500 ms hold in the 30,9,40,360,360,120 profile, the 25% hip-scale
  model produces only about `0.26 mm` support retreat per support (`0.68 mm`
  at the full 30 mm request), versus the configured 9 mm stance stroke;
  at 50% scale the corresponding values are about `0.53 mm` and `1.36 mm`;
- SEARCH freezes the release hip and changes only knee, so a model release
  near `(42.20,-60)` returns near `(8.11,-100)` rather than preserving the
  release X.

These are offline model calculations, not claims of measured link geometry.
They are sufficient to explain the reported forward-lean accumulation:
hidden X drift during lift/search is admitted into `s_quad_demo_foot`, while
support compensation is based only on the much smaller post-lift FK residual.

Test-gap correction
-------------------
The current tests pass because they assert the regressed semantics directly:

Deep causes corrected:

- A fixed hip near a vertical shank has two same-sign knee roots for one
  elevated Z. Nearest-root selection could decrease the knee from a retreated
  start and later jump to the other root, producing the observed apparent
  backward fold and intermittent invalid frames. Live LIFT now selects the
  root that moves in the configured knee direction; short releases retrace
  that exact arc.
- Live SWING is now an explicit horizontal foot-space segment at fixed Z and
  full IK. Post-swing SEARCH preserves release X and lowers Z with full IK.
- Total support demand is `sum(moving foot x - its takeoff x) / support_count`,
  including LIFT, SWING and SEARCH. This gives `/3` for one moving leg and the
  sum `/2` for a diagonal pair. Each support still clamps independently.
- Support capacity previously tested a distant endpoint and binary-searched
  under a false monotonic-safety assumption. It now scans outward from zero
  and stops at the first unsafe prefix, so a later safe island cannot hide an
  intermediate pulse-limit violation.

  knee-first lift from `(0,-100)` reaches approximately `(38.13,-60)`, which

ARD-1 first offline engineering slice (2026-09-14)

and SEARCH do not create body drive. A diagonal pair uses the leading swing's
single D value, and each support receives the same `-D` request before its own

ARD-1 second offline engineering slice (2026-09-14)
-----------------------------------------------------
The first-slice release discontinuity was fixed by adding a latched
`body_drive_floor_mm` to the live state. When a held leg enters SEARCH, the
already achieved body drive remains active, so support feet hold their last
commanded x instead of returning to their support origin. A rebase is performed
only after the landing pose has been written; when no moving legs remain, the
drive reference and latch are cleared.

The live target is now bounded at `plan.step_length_mm`. Body drive is separate
from visible swing and is currently `35%` of the largest accepted horizontal
swing among held legs. Each support gets the same nominal `-D` request, then
uses an independently cached prefix-safe retreat reserve with an `85%` margin;
one support reaching its reserve does not stop the others. The previous
KFC-1/global-conservation semantics are not used by this ARD-1 path.
